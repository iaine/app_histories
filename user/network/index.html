network: the tracker call graph

network records, for every app, which code calls into third-party tracker SDKs and what the tracker code calls in turn:

app code  ->  tracker SDK  ->  network API / framework / library

It then combines every app into one GEXF file for Gephi or networkx, with a timeline: each node and edge records the versions it exists in.

# 1. metadata first: this is where the tracker lists come from
cim-apps metadata --apk-dir apks/ --outdir results/

# 2. the tracker call graph
cim-apps network --input-dir results/ --apk-dir apks/ --outdir results/

--input-dir is the directory of *.metadata.jsonl files. Their tracker lists are read once into a single shared set, and every APK is scanned for the whole set.

Outputs

File Contents
<apk>.network.jsonl one record per app: pkg, version, version_code, graph.nodes, graph.links, summary
network.gexf every app combined, written after the last APK (--gexf FILE to rename)

Node kind is one of:

  • tracker: a method in a tracker package, with tracker (signature) and category
  • app: code shipped in the APK outside every tracker (the app and its bundled libraries)
  • network_api: OkHttp, Retrofit, HttpURLConnection, sockets, gRPC, Volley, WebView.loadUrl
  • external: anything the APK only refers to (the Android framework, the JDK)

Link kind is calls_tracker, tracker_calls, network, tracker_to_tracker or internal. weight is the number of call sites. In the GEXF file the link kind is called relation, because GEXF reserves kind for something else.

In the combined graph, tracker, network and external nodes are shared between apps, so two apps using the same SDK meet at the same nodes; apps says how many apps a node or edge was seen in and releases how many (app, version) pairs. App-code nodes are kept apart per app (<pkg>::<id>), because two apps both having a class La/b; share only an obfuscated name. They are not kept apart per version, so a method that survives from one release to the next is one node.

Timeline

The time axis is the Android version code, the number that increases with every release of an app. Put several versions of the same app in --apk-dir and open network.gexf in Gephi: the timeline is enabled, and sliding it shows tracker calls appear and disappear between releases.

  • Something seen in release v exists from v until just before that app's next release in the corpus.
  • In an app's newest release it runs to the end of the timeline.
  • Something present in versions 10 and 30 but not 20 gets two spans, so it visibly leaves and comes back.

Version codes are only comparable within one app. Three unrelated test apps had codes 72, 26,392 and 186,088, so on a shared axis they sit far apart for no meaningful reason. The timeline is for following one app (or a few) through its releases, not for comparing different apps by date.

Records written before version codes were added have no place on the timeline; the merge warns about them. Re-run those APKs with --force.

Options

  • --level class gives one node per class instead of per method. On three test apps this cut the graph from 32,683 edges to 14,126. Obfuscated method names change between releases more than class names do, so this level also gives steadier timelines.
  • --include-internal keeps calls that stay inside one tracker. They are dropped by default: they were nearly half of all edges on a real app.

Embeddedness per era: network-embed

How deeply is each tracker wired into an app, and how does that change across releases? network-embed answers from the *.network.jsonl files already written. It opens no APK and takes under a second.

cim-apps network-embed --input-dir results/
cim-apps network-embed --input-dir results/ --era minor --csv eras.csv

It writes network.embeddedness.csv, one row per app, era and tracker.

Releases are grouped into eras by version name:

--era 3.103.0-6392 falls in
major (default) 3.*
minor 3.103.*
release 3.103.0-6392 (no grouping)

Major versions are not a consistent unit: one app reaches 43.x while another stays on 3.x for years. Choose the level that splits each app into a useful number of eras, and compare eras within an app only.

Column Meaning
releases, releases_present, presence releases in the era, how many contain the tracker, and that share
app_callers distinct methods outside the tracker that call it
call_sites how many times they call it
entry_points distinct tracker methods they call: how much of its API is used
tracker_nodes distinct tracker methods in the graph
apk_code_called distinct methods elsewhere in the APK that the tracker calls
network_apis, network_call_sites network classes the tracker reaches, and how often
other_trackers other trackers it calls
app_caller_share app_callers divided by all methods scanned (method level only)

Each count is the mean over the releases in which the tracker is present. presence is kept apart so that "in half the releases" is not mistaken for "half as embedded".

Things to bear in mind:

  • "App" means everything in the APK outside the tracker packages, bundled libraries included. They cannot be separated reliably once an app is obfuscated.
  • These are counts, not a centrality score. Eigenvector centrality is all zeros on a one-way call graph, and its scores cannot be compared between eras.
  • Run every release at the same --level. Method-level and class-level counts are not comparable, and the command warns if an era mixes them.

SLURM arrays

With --task-count above 1 no shard writes the combined graph. Run the merge once the array has finished:

cim-apps network-merge --outdir results/

Cost

One pass over the bytecode: about 40 seconds and 0.9 GB for a mid-sized app (Otter, 312,000 methods). Very large apps take several times that, so keep --workers low for them.

Limits

  • An edge means "this method contains a call to that one". Interface dispatch and reflection are not resolved, so the graph under-reports.
  • Only trackers already named in the metadata results are searched for.
  • Shared tracker nodes are matched by name. Two SDK versions that obfuscate an internal method to the same name are merged.
